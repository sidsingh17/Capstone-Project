Criterion 01
Problem Understanding & Domain Alignment
Clarity of business problem and domain relevance
Q
What is the core business problem this system addresses?
Supply chain managers across global operations face a critical intelligence gap — operational risk data is scattered across procurement systems, shipment records, warehouse platforms, and vendor reports. Manually consolidating this information is time-intensive and reactive. The system solves this by enabling operations teams to:
  • Query historical supply chain incidents using natural language (no SQL, no dashboards)
  • Automatically surface similar past disruptions through semantic retrieval
  • Receive AI-generated, explainable mitigation recommendations within seconds
  • Detect anomalies and proactively flag emerging risk patterns before disruption occurs
Q
Which real-world supply chain scenarios does the system handle?
The system directly addresses the five key disruption patterns stated in the problem statement:
Business ScenarioSystem Capability
"Supplier delivery delays increasing"Supplier Risk Agent + semantic search over delay incidents
"Port congestion impacting schedules"Shipment Analysis Agent + hybrid search on port/transit records
"Inventory approaching stockout"Inventory Intelligence Agent + stockout risk scoring
"Transportation costs spiked unexpectedly"Anomaly detection flags cost outliers; demand risk dimension
"Demand spikes causing fulfillment bottlenecks"Inventory agent demand-vs-supply gap analysis
Q
How does the system go beyond traditional threshold-based monitoring?
Traditional systems trigger alerts when a metric crosses a fixed threshold (e.g., delay > 5 days). This system advances beyond that in three ways:
  1. Semantic understanding: Natural language queries find conceptually similar incidents — not just keyword matches. "Component shortage causing production risk" retrieves supplier delays, quality issues, and demand spikes.
  2. Contextual risk scoring: Risk is computed across four correlated dimensions simultaneously — a single late shipment is LOW risk, but when combined with low inventory and a forecasted demand spike, it becomes CRITICAL.
  3. Proactive intelligence: IsolationForest detects anomalous operational patterns before they become disruptions, and the Recommendation Agent generates forward-looking proactive alerts.
Domain Alignment: The system is designed around the actual workflow of an operations manager — from noticing a problem ("supplier delays increasing"), to querying the system conversationally, to receiving a ranked list of similar historical incidents with specific, actionable mitigation steps tied to real owners and timelines.

Criterion 02
Data Engineering & Processing
Dataset usage, preprocessing, metadata extraction, chunking strategy
Q
What dataset is used and what does it contain?
The system uses Supply Chain Logistics Dataset (supply_chain_data.csv) — 600 synthetic supply chain incident records spanning January 2024 to May 2026. It contains 16 fields including: supplier_id (S001–S020) warehouse_location (12 US cities) shipment_status delivery_delay (days) inventory_level (units) transportation_cost (USD) incident_type (8 types) severity (4 levels) incident_description (RAG text field)

The dataset is generated using a probabilistic simulator (generate_sample.py) that replicates real supply chain disruption distributions — e.g., exponential delay distributions, correlated inventory-demand patterns.
Q
How is data preprocessed before indexing?
The preprocessing pipeline (preprocessing.py) executes five steps:
  1. Type coercion: pd.to_numeric(..., errors='coerce').fillna(0) for numeric fields
  2. String normalisation: Strip whitespace, fill nulls with "Unknown" for categorical fields
  3. Deduplication: Remove duplicate rows by incident_id
  4. Timestamp parsing: Convert to YYYY-MM-DD string for metadata consistency
  5. Feature enrichment: Computed fields added — risk_score (row-level 0–1 score), inventory_turnover (inventory ÷ order_qty), delay_ratio (delay ÷ resolution_time)
Q
What is the chunking strategy and why was it chosen?
The system uses a row-per-document strategy — each CSV row becomes exactly one structured document. The document content combines the natural language description with structured metadata fields:
[incident_description]. Incident Type: [type]. Supplier: [id]. Warehouse: [location]. Region: [region]. Status: [status]. Severity: [severity]. Delivery Delay: [N] days. Inventory Level: [N] units. Transportation Cost: $[N]. Date: [date]

Why row-per-document over sliding window? Each CSV row is a complete, self-contained incident event with a natural semantic boundary. Splitting rows would lose the event-level context. At ~60–80 tokens per document, all records fit well within both the OpenAI text-embedding-3-small (8191-token limit) and the fallback all-MiniLM-L6-v2 (256-token limit) without truncation. Token counts are stored in metadata using tiktoken cl100k_base for downstream budget management.
Q
How is metadata extracted and used for filtering?
Every document carries a rich metadata dictionary stored alongside its embedding vector. Metadata fields are used for pre-retrieval filtering via structured $where queries:
Metadata FieldFilter OperatorUse Case
supplier_id$eq "S003"Focus analysis on a specific supplier
severity$eq "critical"Return only critical incidents
shipment_status$eq "Delayed"Filter to delayed shipments only
warehouse_location$eq "Chicago, IL"Regional analysis
incident_type$eq "Port Congestion"Incident-type-specific queries
Filters reduce the ANN search candidate space before scoring — this improves both precision and performance.

Criterion 03
RAG & Retrieval Quality
Hybrid search, semantic retrieval, relevance of retrieved information
Q
What retrieval strategy is implemented and why hybrid over semantic-only?
The system implements hybrid retrieval combining BM25 sparse search and semantic dense search, merged via Reciprocal Rank Fusion (RRF). Neither approach alone is sufficient:
MethodStrengthWeakness
BM25 (keyword)Exact matches: supplier IDs (S003), incident types (Port Congestion), warehouse namesMisses synonyms, paraphrasing, conceptual similarity
Semantic (embedding)Conceptual similarity: "component shortage" ↔ "supply disruption"Fails on rare terms, exact entity matching, codes
Hybrid RRFBest of both — entity precision + conceptual recallSlightly more compute (two retrievals)
Q
How does Reciprocal Rank Fusion work mathematically?
RRF combines two ranked lists using only rank positions — no score normalisation needed:
RRF_score(doc) = α × 1/(k + rank_semantic) + (1-α) × 1/(k + rank_bm25)
Where: α = 0.5 (configurable), k = 60 (standard constant)
The constant k=60 prevents the top-ranked document from dominating. Both ranked lists are merged (union), and documents appearing in only one list get score contribution from that list only. Final results are sorted descending by RRF score and sliced to top_k.

Why not linear combination? BM25 scores are unbounded (corpus-dependent TF-IDF weights), making direct weighted addition unreliable. RRF is robust to score scale differences.
Q
What is the logistics-aware reranker and how does it improve results?
After RRF fusion, a lightweight domain-specific reranker applies field-match boosts before returning results. For each candidate document, if the query string contains an exact match for any of these high-signal fields — incident_type, severity, warehouse_location, supplier_id, product_category — a +0.05 boost is added to the RRF score per matched field.

Example: Query "critical delay from supplier S003 in Chicago" — documents with severity=critical, supplier_id=S003, warehouse=Chicago all receive boosts, surfacing the most contextually precise results to the top ranks.
Q
How is the embedding model chosen and what is its role?
The primary embedding model is text-embedding-3-small (OpenAI, 1536-dim), accessed via the keygateway endpoint. A fallback to all-MiniLM-L6-v2 (sentence-transformers, local, 384-dim) is automatically activated if the gateway /embeddings endpoint is unreachable: 1536 dimensions (primary) 384 dimensions (fallback) OpenAI text-embedding-3-small (primary) all-MiniLM-L6-v2 local (fallback) L2-normalised output

On startup, the system probes the gateway. If reachable, OpenAI embeddings are used for both ingestion and query encoding. If unreachable, sentence-transformers loads locally. The vector store stores a store_meta.json with model/dimension info — if a mismatch is detected on restart (e.g., switching from 384-dim to 1536-dim), the store auto-clears and re-ingests to prevent dimension errors. L2-normalisation allows cosine similarity via dot product: embs_normed @ q_norm.
Retrieval Quality Baseline: In live testing, the hybrid search returns semantically relevant incidents within 12–15ms for the 600-document corpus. Metadata filtering correctly narrows results to the specified supplier, region, or severity without false positives.

Criterion 04
Agentic AI Design
Multi-agent architecture and agent orchestration quality
Q
Describe the multi-agent architecture and each agent's responsibility.
The system implements a hierarchical parallel multi-agent architecture with four specialised agents:
AgentSpecialisationTools AvailableEscalation Trigger
SupplierRiskAgentDelivery performance, SLA compliance, single-source dependencyget_supplier_history()risk_score > 0.7
ShipmentAnalysisAgentRoute disruptions, port congestion, carrier capacityget_route_status()Critical delay patterns
InventoryIntelAgentStockout prediction, demand-supply gap, safety stockcheck_inventory() get_demand_forecast()Any warehouse < 50 units
RecommendationAgentCross-agent synthesis, conflict resolution, proactive alertsNone (synthesis-only)Consolidated risk > 0.85 → Director
Q
How is tool use (function calling) implemented in agents?
Each agent uses OpenAI function calling with a two-turn conversation loop:
  1. Initial call with tools=[...] and tool_choice="auto"
  2. If response.choices[0].message.tool_calls is present: execute tool, append results as role="tool" messages
  3. Second LLM call with full conversation history (including tool results) for final analysis
Tools are defined in OpenAI function schema format with parameters (JSON Schema). This allows agents to request domain-specific data (supplier history, route status, inventory levels) before making risk determinations — grounding their analysis in additional context beyond what was retrieved.
Q
How does the Agent-to-Agent (A2A) escalation workflow operate?
A2A escalation is a threshold-driven notification chain between agents, implemented in the Orchestrator:
  1. After the parallel phase, any agent with risk_score > 0.7 sets escalated=True
  2. The Orchestrator logs a chain entry: "AgentName → RecommendationAgent: [reason]"
  3. If the average risk score across all escalated agents exceeds 0.85, a second entry is appended: "RecommendationAgent → Operations Director: Critical multi-agent escalation"
  4. The RecommendationAgent receives the escalation context in its input, allowing it to weight synthesis toward the highest-risk findings
  5. The complete escalation_chain is returned in the API response for full auditability
Q
How is agent parallelism achieved and what happens if an agent fails?
Parallelism: Python's ThreadPoolExecutor(max_workers=3) submits all three specialist agents simultaneously. Since LLM API calls are I/O-bound (network wait), threads release the GIL during the wait — achieving effective concurrency. Wall-clock time ≈ slowest single agent, not the sum.

Fault isolation: Each future is wrapped in a try/except block. If an agent raises any exception (timeout, API error, parsing failure), the Orchestrator inserts a stub AgentResult with risk_score=0.0 and "Manual review required" recommendation — preventing one failed agent from crashing the entire analysis. The RecommendationAgent still synthesises from the available results.

Criterion 05
Recommendation / Intelligence Quality
Root cause analysis, prediction quality, recommendation explainability
Q
How are mitigation recommendations structured for explainability?
Every recommendation is generated in a structured 5-part format enforced by the prompt:
FieldExample ValuePurpose
Priority1 (highest urgency)Tells the manager what to do first
Action"Activate backup supplier S007 for critical components"Specific, non-generic action step
TimelineImmediate / 24h / Week / MonthUrgency and planning horizon
OwnerProcurement Team / Logistics ManagerClear accountability assignment
Expected Impact"Restore 80% supply capacity within 48h"Quantified outcome expectation
Recommendations are also accompanied by the full risk factor list explaining why the risk score was computed — e.g., "Critical supplier delays averaging 11.2 days detected in 4 of 6 retrieved incidents."
Q
How does the system perform root cause analysis?
Root cause analysis is performed at two levels:
  1. Metric-level (Risk Scoring): The four-dimension risk scorer isolates which operational dimension is driving risk — if inventory_risk=0.95 but supplier_risk=0.15, the root cause is clearly stock depletion, not supplier performance.
  2. Pattern-level (Agent Analysis): Each specialist agent is prompted to identify root causes in their domain. SupplierRiskAgent identifies whether delays stem from production issues, raw material shortages, or quality holds. ShipmentAnalysisAgent traces whether delays originate at the port, in customs, or with the carrier.
The RecommendationAgent synthesises both levels into a narrative: "High inventory risk driven by 6-day supplier delay at S003 coinciding with peak Q4 demand — stockout window is 8 days."
Q
How does evidence grounding ensure recommendation quality?
The RAG pipeline grounds every recommendation in retrieved historical evidence through three mechanisms:
  1. Context injection: Up to 8 retrieved incidents (trimmed to 8,000 tokens) are embedded directly in the GPT-4o-mini prompt — the model generates recommendations based on actual past disruptions, not hallucinated patterns.
  2. Faithfulness enforcement: The LLM-as-judge evaluation explicitly scores Evidence-Based (0–10): "Are recommendations grounded in the historical data?" — low-scoring responses are flagged.
  3. Risk factor attribution: Every risk score comes with a risk_factors list identifying which specific metric and threshold triggered each dimension — creating a complete audit trail from query to recommendation.
Proactive Intelligence: The RecommendationAgent generates PROACTIVE_ALERTS — forward-looking warnings not directly asked for. Example: "Port congestion at LA typically peaks Q4 — pre-position inventory 6 weeks ahead to maintain safety stock." This transforms the system from reactive to proactive risk management.

Q
How scalable is the architecture?
The system is designed with horizontal and vertical scalability paths:
  • Stateless API: FastAPI workers share no in-memory state — multiple Uvicorn workers or Docker replicas can run behind a load balancer
  • Vector store abstraction: VectorStore class hides implementation — swap numpy (development) for Pinecone/Weaviate (production) by changing only vector_store.py
  • Agent parallelism: ThreadPoolExecutor(max_workers=3) configurable via environment for larger agent fleets
  • Configurable LLM: LLM_MODEL env var switches between GPT-4o-mini (cost) and GPT-4o (quality) without code changes
  • Batch ingestion: 100-doc batches allow large dataset ingestion without memory spikes
Q
What are the API design principles?
The API follows REST conventions with production-grade practices:
  • Versioned namespace: All endpoints under /api/v1/ — future v2 can coexist
  • Pydantic v2 validation: Every request and response is schema-validated — invalid inputs return structured 422 errors, not 500s
  • Consistent error responses: All error paths return {"error": "...", "detail": "...", "code": N}
  • OpenAPI auto-docs: Swagger UI at /docs, ReDoc at /redoc — generated automatically from Pydantic schemas
  • CORS: Configured for frontend-backend separation, restrictable to specific origins in production
  • Health endpoint: GET /api/v1/health returns vector store status, LLM connectivity, and document count for monitoring

Criterion 07
Evaluation Framework
DeepEval, LLM-as-judge, validation methodology
Q
How is DeepEval integrated and what metrics does it measure?
DeepEval is integrated in evaluation_service.py and triggered via the evaluate_quality=true flag on the POST /recommendations endpoint. It measures four standard RAG quality metrics:
MetricWhat It CatchesThreshold
Answer RelevancyDoes the response address the actual query?≥ 0.5
FaithfulnessAre claims grounded in retrieved context (no hallucination)?≥ 0.5
Contextual PrecisionAre the retrieved documents relevant to the question?≥ 0.5
Contextual RecallDoes the context cover all information needed to answer?≥ 0.5
The system gracefully degrades — if DeepEval is not configured, a placeholder response is returned without crashing the recommendation pipeline.
Q
How does the LLM-as-judge work and what does it evaluate?
The LLM-as-judge uses GPT-4o-mini as an independent evaluator of recommendation quality. It scores responses across five supply chain-specific dimensions (0–10 each):
  1. Relevance — Are recommendations directly tied to the identified risk?
  2. Actionability — Can the operations team execute these steps immediately?
  3. Completeness — Are all major risk dimensions (supplier, inventory, shipment, demand) addressed?
  4. Feasibility — Are the timelines and owners realistic for the organisation?
  5. Evidence-Based — Do recommendations reference or align with the historical incident data?
The judge returns an APPROVED / NEEDS_IMPROVEMENT / REJECTED verdict plus a 0–10 overall score. This is the key difference from DeepEval — it evaluates business value, not just RAG pipeline quality.
Q
What other validation mechanisms exist beyond DeepEval?
The evaluation framework operates at three levels:
  1. Input validation (Guardrails): Three-layer check ensures queries are valid, injection-free, and domain-relevant before any LLM call — prevents garbage-in-garbage-out at source
  2. Statistical validation (Anomaly Detection): IsolationForest validates that operational patterns detected in the data are statistically anomalous, not arbitrary — Pearson correlation analysis confirms the anomalies are correlated with known disruption drivers
  3. Unit tests: test_search.py validates guardrails and risk scoring logic with known-input assertions; test_agents.py validates agent output parsing and orchestrator risk consolidation
Why dual evaluation (DeepEval + LLM Judge)? DeepEval catches technical RAG failures (hallucination, irrelevant retrieval). The LLM judge catches business quality failures (generic recommendations, infeasible timelines, missing risk dimensions). Both are needed — a response can be faithful and relevant but still operationally useless.

Q
How is the codebase structured for maintainability?
The codebase follows single-responsibility layered architecture — each module has one clear job:
  • Abstractions at boundaries: VectorStore hides the embedding storage backend — switching from numpy to Pinecone changes only one file. BaseSupplyChainAgent means adding a new agent is just a subclass with system_prompt, tools, and analyze()
  • No hardcoded values: All configuration (model name, top_k, alpha, contamination) is in Settings (pydantic-settings) and loaded from .env — change behaviour without touching code
  • Idempotent operations: Ingestion checks count before re-indexing; upsert semantics in VectorStore prevent duplicate documents
  • Consistent error handling: All API routes wrap service calls in try/except blocks, mapping ValueError → 400 and Exception → 500 consistently across all endpoints

Q
Why is SSL verification disabled for the gateway?
The make_openai_client() function in config.py passes httpx.Client(verify=False) when OPENAI_BASE_URL is set. This is necessary because the keygateway (https://keygateway.arshnivlabs.com/v1) uses a TLS certificate issued by a Certificate Authority that is not in Python's certifi trust bundle.

Why curl works but Python httpx does not: curl uses the operating system's native certificate store (Windows CertMgr / Linux ca-certificates), which may include the gateway's CA. Python's certifi ships its own CA bundle independent of the OS store — the gateway's CA is absent from it, causing an SSLCertVerificationError. Disabling verification is an acceptable development-environment workaround since the gateway is a known, trusted internal endpoint.

Production fix: The correct production solution is to add the gateway's CA certificate to the certifi bundle (or provide a custom CA via ssl_ca_cert) rather than disabling verification globally. The environment variable OPENAI_BASE_URL controls whether the workaround is applied — standard OpenAI API calls (no custom base URL) use the default verified client.

  • OPENAI_BASE_URL=https://keygateway.arshnivlabs.com/v1
  • LLM_MODEL=gpt-4o-mini
  • EMBEDDING_MODEL=text-embedding-3-small
  • MAX_TOKENS=500 (gateway hard cap — exceeding causes errors)

Q
What are the most likely panel questions and their answers?
Q: "Why use hybrid search instead of just vector search?"
A: Semantic search alone misses exact entity matches — if an operations manager searches "supplier S003", pure semantic search may return conceptually related but wrong suppliers. BM25 handles exact codes and names precisely. RRF combines both without score normalisation overhead.

Q: "How do you prevent hallucinations in recommendations?"
A: Three layers: (1) Retrieved incidents are injected directly into the prompt as grounding context. (2) DeepEval Faithfulness metric flags responses that make claims unsupported by the context. (3) LLM-as-judge scores Evidence-Based dimension — low scores are surfaced to the user.

Q: "Why not use a managed vector database like Pinecone?"
A: The VectorStore is fully abstracted — the Pure-Numpy implementation is a deliberate choice for Python 3.13 / Windows compatibility (ChromaDB requires MSVC build tools not available in Python 3.13 on Windows). In production, only vector_store.py changes — the rest of the stack is unaffected. Pinecone or Weaviate would be the production upgrade path.

Q: "How does the system scale to 10 million incidents?"
A: Replace the numpy store with Pinecone (managed ANN at scale), run multiple Uvicorn workers behind a load balancer, use Redis caching for frequent queries. The BM25 index would move to Elasticsearch. The agent and RAG logic remains unchanged.
Q
What are the key differentiators of this project versus a basic RAG system?
Hybrid Search with RRF — not just semantic, combines keyword + embedding + domain boost
Multi-dimensional Risk Scoring — 4 weighted dimensions, not a single score
Multi-Agent Parallelism — 3 specialist agents run concurrently, not sequentially
A2A Escalation Chain — agents communicate and escalate to director level automatically
Dual Evaluation — DeepEval (RAG quality) + LLM-as-judge (business quality)
Token Budget Management — tiktoken-based context window control prevents truncation errors
IsolationForest Anomaly Detection — statistical anomaly detection beyond threshold alerts
Proactive Alerts — system surfaces risks the user did not explicitly ask about
